# Мост к подписке Grok

OpenAI-совместимый эндпоинт на `127.0.0.1:8318`, за которым живёт подписка Grok. Нужен, чтобы
профили `grok` и `grok46` в `Resources/Prototypes/_AiAgent/llm_profiles.yml` были обычными
профилями, а не особым случаем внутри игрового сервера.

## Зачем он существует

Игровой клиент моделей (`Content.Server/AiAgent/Llm/LlamaClient.cs`) умеет ровно одно:
`POST {endpoint}/chat/completions`, `stream: false`, ключ в `Authorization`. Подписка Grok не
подходит по трём пунктам сразу, и ни один из них не косметический.

1. **Адрес и заголовки.** Подписка отвечает на `https://cli-chat-proxy.grok.com/v1` и требует
   `X-XAI-Token-Auth: xai-grok-cli` плюс `x-grok-model-override: <модель>`. Второй заголовок —
   не дубликат поля `model`: **маршрут выбирается именно им**, и запрос без него уедет на модель
   по умолчанию, ответив при этом бодрым HTTP 200. Самая неприятная форма ошибки: раунд идёт,
   всё работает, модель не та.
2. **Только поток.** Почти всё за этим адресом отвечает исключительно SSE. Наш клиент потока не
   читает.
3. **Не ключ, а сессия.** Там OIDC-токен на шесть часов с обновлением по refresh-токену.

Первые два можно было бы внести в игровой сервер — третий нельзя. Обновление токена в игровом
процессе делает его владельцем OAuth-кредов, а у refresh-токена владелец может быть только один:
токен одноразовый и ротируется вендором, поэтому второй обновивший отзывает первого. На этой
машине это уже происходило — `~/.hermes/auth.json` до сих пор хранит `refresh_token_reused` от
07.08.2026. Терминальный `grok` отзывал бы токен у сервера посреди раунда.

Поэтому мост: отдельный процесс, **единственный владелец своей сессии**, и своя эта сессия у него
получена отдельной активацией устройством. Терминальный `grok` (`~/.grok/auth.json`) и мост
(`ai_data/grok.session.json`) обновляют **разные** refresh-токены и потому не мешают друг другу.
Именно ради этого выбрана активация устройством, а не чтение чужого токена.

## Чем он не является

Это **не** CLIProxyAPI, о котором говорит README форка. Тот на этой машине не установлен
(каталога `~/.cli-proxy-api/` нет, порт 8317 никто не слушает), и профиль `codex` до сих пор
указывает в пустоту. Наш мост занимается только Grok и слушает **8318** — чтобы не занимать порт,
закреплённый за ChatGPT-мостом, если его однажды поднимут.

## Файлы

| Что | Где |
|---|---|
| Сервер | `grokbridge.py` |
| Активация и обновление токена | `grokauth.py` |
| Сессия (секрет, 600) | `ai_data/grok.session.json` |
| Ключ доступа к самому мосту (секрет, 600) | `ai_data/grok_bridge.key` |
| Юнит | `grok-bridge.service` → `~/.config/systemd/user/` |
| Тесты склейки потока | `test_assemble.py` |
| Живая проверка | `selftest.py` |

Секреты живут только в `ai_data/` — каталог в `.gitignore`. В `Resources/` их быть не может:
`Content.Server/Acz/ContentMagicAczProvider.cs` раздаёт всю папку каждому подключившемуся игроку.

## Установка

```bash
cd /home/rewin/projects/ss14_ai

# 1. Ключ доступа К МОСТУ (не к подписке). Loopback здесь общий с другими пользователями машины.
umask 077 && head -c 32 /dev/urandom | base64 | tr -d '\n' > ai_data/grok_bridge.key

# 2. Активация устройством: покажет ссылку и код, подтверждение — с телефона.
python3 Tools/grokbridge/grokauth.py login

# 3. Юнит.
cp Tools/grokbridge/grok-bridge.service ~/.config/systemd/user/
systemctl --user daemon-reload && systemctl --user enable --now grok-bridge

# 4. Проверка.
curl -s --noproxy '*' 127.0.0.1:8318/health
python3 Tools/grokbridge/selftest.py --model grok-4.6
```

Профили `grok`/`grok46` уже указывают на 8318 и на `keyFile: grok_bridge.key`; после этого
цепочка включается на живом сервере одной командой:

```
cvar ai.llm_chain "grok46,grok,local"
```

Отдельным агентам цепочка задаётся своим полем `llmChain` (у прототипов боргов) — глобальный
cvar они перекрывают, см. `AgentBody.LlmChain`.

## Эксплуатация

```bash
curl -s --noproxy '*' 127.0.0.1:8318/health          # срок сессии, есть ли refresh
journalctl --user -u grok-bridge -f                  # ходы: модель, время, число вызовов
python3 Tools/grokbridge/grokauth.py status          # то же без запущенного моста
python3 Tools/grokbridge/grokauth.py login           # повторный вход, мост перезапускать НЕ надо
```

Повторный вход подхватывается на лету: мост перечитывает файл сессии по `mtime`, а не держит его
в памяти навсегда.

## Что проверено и чем

`test_assemble.py` (12 тестов, без сети) — склейка потока в один ответ. Это единственное место,
где мост может соврать незаметно: оборванный аргумент вызова инструмента не выглядит ошибкой, он
выглядит как решение агента, и разбирать такое по журналам раунда — самая дорогая отладка, какая
бывает. Проверяются куски аргументов, два параллельных вызова, имя, повторённое в каждом кадре,
вызов без индекса, битый кадр, пустой поток и `usage`.

```bash
cd Tools/grokbridge && python3 -m unittest discover -s .
```

`selftest.py` — четыре вопроса, ответы на которые знает только вендор: знает ли он `grok-4.6`,
переживает ли наш набор полей, отдаёт ли вызов инструмента в ожидаемом виде и сообщает ли
`usage`. Тратит квоту (два коротких хода), поэтому отдельно от юнит-тестов.

Прогон 19.08.2026: все четыре зелёные, `usage` приходит, `goto({"handle":"door-11"})` собирается
из потока правильно. `GET /v1/models` через мост отдаёт ровно две модели — `grok-4.6` и
`grok-4.5`, то есть оба профиля обеспечены, и третьей записи в `llm_profiles.yml` взяться неоткуда.

## Два отказа, которых нет в документации вендора

Оба найдены вживую, оба выглядят как «мост не работает», и оба чинятся в одну строку — если
знать, где искать. Ради этого они здесь и записаны.

**HTTP 426, «Your Grok CLI version (none) is outdated».** Прокси проверяет, кто к нему пришёл,
и требует `x-grok-client-identifier` и `x-grok-client-version`. В README самого CLI перечислены
только три заголовка (`Authorization`, `X-XAI-Token-Auth`, `x-grok-model-override`), и запрос,
собранный строго по этому описанию, не проходит вообще. Имена вытащены из бинарника:
`strings ~/.grok/downloads/grok-linux-x86_64 | grep x-grok-client`.

Версию мост берёт из `~/.grok/version.json`, а не зашивает в код. Порог вендор поднимает, и
захардкоженное число однажды дало бы 426 посреди раунда; обновился `grok` — обновился и мост.
Перекрыть можно переменной `GROK_BRIDGE_CLIENT_VERSION`. Это единственная связь с `~/.grok`, и
она только на чтение одного числа.

**HTTP 403, «OAuth2 token missing required scope: api:access».** Пускающих scope два, а не один:
`grok-cli:access` открывает прокси, `api:access` — саму модель за ним. Коварство в том, что вход
без второго проходит успешно, токен выдаётся, `/health` зелёный — и отказ приходит только на
первом настоящем ходу. Расширить scope у выданной сессии нельзя: refresh-грант их не добавляет.
Лечится новым входом устройством, и список scope правится только вместе с ним.

## Грабли

1. **Два разных ключа.** `ai_data/grok_bridge.key` — это пропуск в мост, а не в подписку.
   Подписка живёт в `ai_data/grok.session.json`, и её содержимое в профили не попадает никогда.
2. **Порядок таймаутов.** У профиля 240 секунд, у моста 300. Сдаться первым обязан игровой
   сервер: иначе в журнале останется обрыв соединения вместо внятного таймаута с именем профиля.
   Меняя одно, поменяйте второе.
3. **Белый список полей.** Наверх уходит только то, что перечислено в `FORWARDED_FIELDS`. Наш
   клиент шлёт `cache_prompt` и `id_slot` для llama.cpp, а строгая API отвечает на незнакомое
   поле 400 — и «провайдер лежит» становится не отличить от «провайдер не понял четвёртое поле».
   Новое поле, которое действительно нужно вендору, надо добавить в список руками; всё
   выброшенное пишется в журнал.
4. **`usage` может пропасть.** Мост просит `stream_options.include_usage`; если вендор такого не
   знает, мост один раз это записывает в журнал и больше не просит. Тогда `aiagent cost` покажет
   нули — не поломка, но и узнать, куда ушла недельная квота, станет нечем.
5. **Правило единственного владельца остаётся в силе.** Не подсовывайте мосту `~/.grok/auth.json`
   и не копируйте его сессию обратно в CLI. Смысл двух активаций в том, что у каждого свой
   refresh-токен.
6. **Квота у `grok` и `grok46` одна.** Это один недельный пул xAI на все продукты Grok; два
   профиля его не удваивают, а вот считают раздельно — суммируйте, глядя на `aiagent llm`.
7. **Прокси не наследуется, и это правильно.** `auth.x.ai` и `cli-chat-proxy.grok.com` отвечают
   с этой машины напрямую (проверено). Немецкий выход включается переменной `GROK_BRIDGE_PROXY`,
   если однажды понадобится.
8. **Размышления не попадают в реплику.** `reasoning_content` собирается отдельно и в `content`
   не подмешивается: склейка превратила бы внутренний монолог злого ИИ в его речь в общем эфире.
9. **Мост не стартует без файла ключа.** Это сделано нарочно. Тихо открытый мост — это чужой
   расход недельной квоты, заметный только по счётчику.
