# Правки движка в этом форке

Здесь учтена **каждая** правка `RobustToolbox/`. Форк держится на правиле «ни одного изменённого
файла апстрима»: игровая логика живёт новыми `EntitySystem`, конфиг — своим `[CVarDefs]`,
прототипы — своими YAML. Всё, что это правило нарушает, попадает сюда — с воспроизведением,
замером и оценкой риска, то есть уже в той форме, в какой это уходит апстримом.

Проверить, что список полон:

```sh
cd RobustToolbox && git status --short
```

Каждый изменённый файл обязан иметь запись ниже. Файл без записи — либо забытая правка, либо
случайная: и то и другое чинится до коммита, а не после.

Сами правки помечены в коде комментарием, начинающимся со слов `FORK PATCH`:

```sh
cd RobustToolbox && git grep -n "FORK PATCH"
```

## Болезнь, ради которой сделаны все правки

Клиент попадает в петлю: сервер шлёт дельту сущности, которой у клиента нет, клиент бросает
`MissingMetadataException`, просит полное состояние, получает его — и всё повторяется. Снаружи это
выглядит как «сервер завис»: игра стоит, а в логе только предупреждения.

Строка, по которой это считается:

```
[WARN] system.pvs: Client rewin123 requested full state on tick 13348. Last Acked: 13400.
Curtick: 13402. Apparently they received an entity without metadata: Клин (52798, AiBorgCombatChassis).
```

Мерить голым числом строк за раунд нельзя: раунды разной длины и с разным числом игроков, и раунд
вдвое короче честно даёт вдвое меньше строк при вдвое худшей игре. Сравнимая величина одна —
**ресинков на 1000 тиков на игрока**, её считает `Tools/pvs_resync_report.py`.

| замер | ресинков на 1000 тиков на игрока |
|---|---|
| раунд 161 (до правки `ai.borg_pvs_override`) | 1.1 |
| раунд 162 (с постоянной репликацией тел роботов) | 17.4 |
| 21.08.2026, после патча №1 | 6.71 |
| 21.08.2026, после патчей №2 и №3 | 0 |
| **23.08.2026, боевой раунд 4.5 часа, двое игроков** | **3.31** |

Патч №1 закрыл разрушение мира клиента, №2 — ложный порог MTU, №3 — подтверждение авансом
по размеру, №4 — историю короче пинга клиента, из-за которой №3 складывал такт.

**Ноль 21.08 был верен и всё же неполон.** Прогон, на котором его сняли, шёл без нагрузки на
канал. Боевой раунд 23.08 дал 3.31, и все потери, кроме единиц, приходятся на движущихся
киборгов. Величина задачи, названная 24.08 на стенде с настоящей задержкой, — **пропускная
способность надёжного канала**: 64 сообщения за круг RTT, то есть 128 КБ/с при MTU 1200 и
RTT 600 мс, против p90 в 335 КБ/с на боевом раунде. Затор из этого превышения и есть то, что
превращает одиночный сбой в петлю: каждое восстановление стоит четверти мегабайта, которую канал
везёт секундами.

**Лечить темпом отправки НЕЛЬЗЯ — проверено и отвергнуто** (раздел «Отвергнуто №5»). Осталось
лечить числом и размером полных состояний; на 24.08.2026 эта работа не закончена.

## Патч №1 — полное состояние не урезается бюджетом входа

**Файл:** `Robust.Server/GameStates/PvsSystem.cs`, метод `GetEntityStates`.

### Что не так в апстриме

`AddEntity` считает бюджет входа (`IsEnteringPvsRange` →
`PvsSystem.ToSendSet.cs:86-89`) **до** ветки `session.RequestedFull` (`:94`). При полном состоянии
`fromTick == GameTick.Zero`, поэтому «входящей» считается каждая сущность; а `ForceFullState`
обнуляет `EntityLastAcked` (`ClearPlayerPvsData`), поэтому каждая попадает ещё и в счётчик новых.
Связывающим оказывается меньший из двух потолков — `net.pvs_budget`, **50 сущностей**, а не
`net.pvs_enter_budget` (200).

На клиенте `ApplyGameState` при `FromSequence == 0` зовёт `PartialStateReset(curState, true)`
(`ClientGameStateManager.cs:426`), которая **удаляет каждую сетевую сущность, отсутствующую в этом
состоянии** (`:1284-1288`).

То есть урезанное «полное» состояние не откладывает работу, а уничтожает мир клиента и заставляет
пересобирать его по 50 сущностей в такт — и каждое из этих состояний снова тяжелее порога надёжной
отправки, то есть снова подтверждается авансом. Петля сама себя кормит.

### Замер

Парный стенд клиент+сервер (`Content.AiBench/PvsResyncTests.cs`), карта Box, `net.pvs_range 17`,
611 сущностей в поле зрения:

| | сущностей у клиента после одного полного состояния |
|---|---|
| штатный бюджет 50 | **54** — 91.2% мира удалено |
| бюджет снят | 611 — не потеряно ничего |

Период петли в боевых логах (40–56 тиков) — ровно время, за которое эти ~600 сущностей уезжают
обратно по 50 в такт.

### Правка

Не выставлять `session.Budget` из cvar'ов, когда `session.RequestedFull`: полное состояние — не
поток, а замена, и на него бюджет не распространяется, ровно как на собственных наблюдателей
клиента (`AddForcedEntities` выше по методу).

### Риск

Один такт с большим состоянием на клиента, запросившего полное. Аргумент про бюджет —
«чтобы клиента не дёргало при всплеске спавна» — здесь не применим: клиент всё равно снесёт и
пересоберёт весь свой мир, и отдать ему мир целиком строго дешевле, чем отдать двенадцатую часть и
удалить остальное.

## Патч №2 — порог надёжной отправки берётся из настроенного MTU

**Файлы:** `Robust.Shared/Network/Messages/MsgState.cs`,
`Robust.Shared/Network/NetManager.cs` (метод `BuildMessage`).

### Что не так в апстриме

```csharp
// Ideally we would peg this to the actual configured MTU instead of the default constant, but oh well...
public const int ReliableThreshold = NetPeerConfiguration.kDefaultMTU - 20;
```

Апстрим сам называет это временным решением. В вендоренном здесь Lidgren
`kDefaultMTU = 508` (`NetPeerConfiguration.cs:45`), то есть порог — **488 байт**, тогда как
боевой конфиг ставит `net.mtu = 1200`. Любое состояние от 489 до 1180 байт объявляется «слишком
большим для ненадёжной доставки» без всякого основания — и это не редкий случай, а почти каждый
такт.

Само по себе это была бы лишь потеря пропускной способности. Но `PvsSystem.Send.cs:61-69`
записывает надёжно отправленное состояние как **подтверждённое** в тот момент, когда отдаёт его
Lidgren, — до того, как клиент что-либо применил:

```csharp
if (msg.ShouldSendReliably())
{
    data.RequestedFull = false;
    data.LastReceivedAck = _gameTiming.CurTick;   // клиент об этом ещё не знает
    ...
}
```

Клиент, который затем состояние потерял или не смог применить (переполнение буфера, отсутствующая
база дельты), остаётся с базой, с которой сервер уже не согласен, и выйти из этого может только
запросив полное состояние.

### Замер

Отчёт по боевому логу 21.08.2026, `Tools/pvs_resync_report.py`:

```
отставание клиента (Last Acked - requested): медиана 36, p90 51, макс 80
Curtick - Last Acked:                       медиана 8,  p90 16, макс 18
```

Сервер считает клиента на **36 тиков впереди** того места, откуда клиент просит восстановиться.
Это и есть объём подтверждённых авансом состояний.

### Правка

Порог перестаёт быть константой и становится свойством сообщения: `NetManager.BuildMessage`
проставляет `MsgState.ConnectionMtu` из конфигурации того peer'а, на который сообщение уходит, ещё
до сериализации и до чтения `DeliveryMethod`. Прежняя константа остаётся под именем
`DefaultReliableThreshold` как запасной путь для случаев без настоящего соединения — прежде всего
для внутрипроцессного `IntegrationNetManager`, который сериализует сообщения без Lidgren.

Проводной формат не меняется, ванильный клиент не замечает ничего: способ доставки выбирает
отправитель, для каждого сообщения отдельно. Порог берётся из `INetChannel.CurrentMtu` — MTU
именно этого соединения, а не из `net.mtu` сервера: ванильный клиент наш cvar не разделяет.

### Риск

Привязка идёт к текущему MTU соединения. При включённом `net.mtu_expand` (по умолчанию выключен)
он может вырасти относительно настроенного. Если кто-то поставит `net.mtu` выше того, что
реально проходит по пути, ненадёжные датаграммы начнут теряться — но ровно так же они
терялись бы и у любого другого трафика с тем же конфигом, и Lidgren отказывается отправлять
ненадёжное сообщение крупнее текущего MTU (`NetConnection.cs:360`), то есть тихой потери не будет.

## Патч №3 — подтверждение авансом только там, где оно задумано

**Файл:** `Robust.Server/GameStates/PvsSystem.Send.cs`, метод `SendSessionState`.

### Что не так в апстриме

Надёжная отправка состояния бывает по двум **разным** причинам, и апстрим смешал их в одном
условии:

```csharp
if (msg.ShouldSendReliably())   // = ForceSendReliably || MsgSize > ReliableThreshold
{
    data.RequestedFull = false;
    data.LastReceivedAck = _gameTiming.CurTick;   // клиент об этом не знает
    ...
}
```

| причина | что она утверждает | можно ли подтверждать авансом |
|---|---|---|
| `ForceSendReliably` — полное состояние либо клиент отстал больше `net.force_ack_threshold` | «историю пора обрезать» | **да, это и задумано**: cvar так и описан — «send the next game state reliably and simply force update the acked tick» |
| `MsgSize > ReliableThreshold` | «состояние не влезает в одну датаграмму» | **нет**: это про доставку, а не про применение |

Надёжная доставка гарантирует, что пакет дойдёт, и ничего не говорит о том, что клиент его
применил. `GameStateProcessor` законно выбрасывает состояния — при переполнении буфера, при
опоздании, при разрыве последовательности.

### Замер

Живой раунд 21.08.2026 с диагностикой из раздела ниже. В **каждой** из 76 строк о ресинке:

```
тик=19555 ack=19591 cur=19619 | Клин | EntityLastAcked=19591, LastLeftView=0, LastSeen=19618
тик=19644 ack=19682 cur=19692 | Клин | EntityLastAcked=19682, LastLeftView=0, LastSeen=19691
тик=20082 ack=20105 cur=20123 | Клин | EntityLastAcked=20105, LastLeftView=0, LastSeen=20122
```

| наблюдение | вывод |
|---|---|
| `LastLeftView = 0` во всех строках | сущность из поля зрения не уходила — оптимизация повторного входа невиновна |
| `EntityLastAcked` = ack сессии | состояние с сущностью числилось подтверждённым |
| `LastRealTick` клиента отстаёт от ack на 23–83 тика | клиент его не применял |
| `CurTick − ack` = 1–28 | порог в 60 тиков не срабатывал, значит подтверждение пришло **по размеру** |

Клиент присылает в запросе `_timing.LastRealTick` — последний **применённый** тик
(`ClientGameStateManager.cs:539`), поэтому разрыв читается однозначно.

**Почему страдают именно движущиеся киборги.** Состояние с созданием сущности живёт в
одном-единственном сообщении. Потеряв его, клиент не соберёт сущность никогда — каждая следующая
дельта приходит «без метаданных». Для уже известной сущности пропущенная дельта безобидна. Отсюда
избирательность: в журнале это роботы, которые подходят к игроку и впервые попадают ему в поле
зрения.

### Правка

Подтверждать и ставить сессию в `PendingAcks` только при `data.ForceSendReliably`. Крупное
состояние по-прежнему уходит надёжно — меняется только то, что сервер больше не считает его
применённым, пока клиент не скажет об этом сам.

### Риск, и он оказался не тем, которого я ждал

История `PreviouslySent` у молчащего клиента не растёт: он упрётся в `net.force_ack_threshold` и
будет подтверждён принудительно первой ветвью. А вот **цена такта** оказалась настоящей и большой.

Подтверждение авансом было не только ошибкой — оно ещё и **удерживало базу дельты у текущего
тика**. Честные подтверждения отпускают её назад, `session.FromTick = LastReceivedAck` отъезжает,
и сборка состояний дорожает. На умолчании в 60 тиков сервер сложился вдвое-втрое:

| `net.force_ack_threshold` | `GameState`, мс/такт | тиков за 50 с | ресинков |
|---|---|---|---|
| 60 (апстрим) | **69.16** | 570 (≈11 Гц) | 0 |
| 15 | **3.32** | 1502 (≈30 Гц) | 0 |

Замер на одном и том же раунде, одна станция, один игрок, три киборга; ручка меняется на живом
сервере, перезапуск не нужен. Разница двадцатикратная, ресинков ноль в обоих случаях.

**Первая оценка риска была неверной.** 69 мс при пороге 60 — не цена честной дельты, а цена
истории в 20 тиков, которая короче задержки ack у клиента с пингом 586 мс. Снижение порога до
15 вернуло 30 Гц ценой того, что этому клиенту сервер снова подтверждал авансом каждый такт.
Настоящее лечение — патч №4. Порог возвращён к 60.

Плюс к разделению «надёжно / подтвердить»: состояние, в котором есть хотя бы одна сущность с
`EntityLastAcked == 0` (`Budget.NewCount > 0`), уходит надёжно, но **без** ack авансом. Создание
живёт в одном сообщении, ванильный клиент потеряв его запрашивает полный мир, и единственное,
что сервер может сделать, не меняя провод — доставить создание. `NewCount` растёт только на
первой подряд идущей отправке, так что надёжный канал не держится всю RTT.

## Патч №4 — история отправок не короче порога принудительного подтверждения

**Файлы:** `Robust.Server/GameStates/PvsData.cs` (`PreviouslySent`),
`Robust.Server/GameStates/PvsSystem.cs` (`SendHistorySize`),
`Robust.Server/GameStates/PvsSystem.Session.cs` (`EnsureSendHistorySize`).

### Что не так в апстриме

`PreviouslySent` — словарь последних отправленных наборов сущностей, по которому
`ProcessQueuedAck` выставляет `EntityLastAcked`. Его размер был прибит к `DirtyBufferSize` = 20
тиков. Это **другое** кольцо: грязные сущности при выключенном PVS. Двадцать тиков при 30 Гц —
667 мс. Комментарий в `PvsSystem.cs` прямо говорил, что клиент с большим пингом будет считаться
так, будто каждая сущность входит в PVS впервые, и что бюджет входа это легко забивает.

Владелец этого форка сидит с пингом 586 мс через США. RTT ≈ 18 тиков, плюс буфер состояний
клиента — около 20. После патча №3 честный ack приходил ровно на границе окна и не находил
sent-set. `EntityLastAcked` застывал, `IsEnteringPvsRange` возвращал entering для всех ~600
видимых тел, сборка состояния стоила 69 мс/такт.

Снижение `force_ack_threshold` до 15 это маскировало: 15 < 20, история ещё видела ack, такт
вставал на 30 Гц — и одновременно 15 < 18, то есть этому клиенту сервер подтверждал авансом
каждый такт. Исходная болезнь создания сущностей вернулась точечно к человеку, ради которого
её чинили.

### Правка

Размер `PreviouslySent` — `max(DirtyBufferSize, ForceAckThreshold + 1)`. Пока клиент внутри
порога, его ack всегда находит sent-set. Порог возвращён к ванильным 60: две секунды хватает
на 586 мс, и сервер больше не врёт про применение. `DirtyBufferSize` не тронут — это кольцо
грязных сущностей, другое.

При живом изменении cvar'а существующие сессии увеличивают историю; уменьшение не сжимает
(большее окно всегда корректно, только тяжелее).

Проводной формат не меняется. Ванильный клиент с любым пингом — как раз тот, для кого это
считается: движок клиента мы не патчим.

### Риск

61 набор вместо 20. На сессию это сотни килобайт, не мегабайты. Если когда-нибудь понадобится
порог в сотни тиков, смотреть память, не корректность.

## Отвергнуто №5 — канальный потолок (`net.pvs_byte_budget`)

> **ОТВЕРГНУТО ЗАМЕРОМ 24.08.2026, умолчание −1 (выключен).** Код и ручка оставлены: они
> стоили дня работы и назвали настоящую величину задачи — потолок надёжного канала. Но сама
> мера делает хуже, и ниже сказано, чем именно.

**Файлы:** `Robust.Shared/CVars.cs` (`net.pvs_byte_budget`, `net.pvs_byte_budget_share`),
`Robust.Server/GameStates/PvsSystem.cs` (`TryTakeSendSlot`, `SessionByteCeiling`),
`Robust.Server/GameStates/PvsSystem.Serialize.cs`, `PvsData.cs` (`SendTokens`, `SentSinceAck`).

### Что не так в апстриме

Понятия «сколько этот клиент увезёт» в PVS нет вовсе: сервер считает состояние и отдаёт его
целиком каждый такт. На локальной сети это незаметно, на длинном канале — нет.

Надёжный канал Lidgren отдаёт **64 сообщения за круг RTT** (`NetConstants.ReliableOrderedWindowSize`).
Это не настройка: приёмник заводит окно того же размера (`NetConnection.cs`, ветки
`ReliableUnordered` и `ReliableOrdered`), поэтому поднять его только на сервере — значит сломать
ванильному клиенту разбор порядковых номеров. При MTU 1200 и RTT 600 мс потолок — **128 КБ/с**.

Дальше складывается затор, и он самоподдерживающийся:

1. сервер предлагает больше потолка — очередь надёжного канала растёт;
2. состояния приходят с опозданием и не по порядку (`ReliableUnordered`), клиент их буферизует;
3. клиент **подтверждает их при ПОЛУЧЕНИИ**, а применить не может: чтобы применить состояние,
   нужна его база, а она в той же очереди;
4. сервер, видя подтверждения, двигает `FromTick` вперёд — и следующие дельты считаются от базы,
   которой у клиента нет НИКОГДА;
5. буфер клиента упирается в `net.max_buffer_size` (512), клиент просит полное состояние,
   выбрасывает всё накопленное — и полное состояние встаёт в тот же затор.

### Замер

Стенд: свой ретранслятор `Tools/laglink.py` (задержка 300 мс в одну сторону, RTT 600 мс),
Release-сборка сервера и клиента, карта Packed, режим `RogueAiOpen` с тремя киборгами, борг
ходит мимо игрока туда-обратно.

Поток к клиенту по замеру самого ретранслятора: **потолок 150 КБ/с** (130 датаграмм в секунду по
1179 Б), медиана датаграммы 1198 Б, 53% пакетов — ровно MTU. Сервер при этом предлагал медиану
53 КБ/с, p90 100 КБ/с и **всплеск 6.3 МБ/с** за одну секунду: сорок секунд затора из одного
кадра.

Клиентская диагностика (см. №10) на том же прогоне печатает то, чего в серверном журнале нет:

```
ВЫБРАСЫВАЮ 513 буферизованных состояний — запрошено полное на тик 29625.
```

**513 состояний при потолке буфера 512** — клиент получил и подтвердил их все и не смог применить
ни одного. Ниже в том же журнале: полные состояния 140–225 КБ, то есть **118–188 фрагментов в
окне из 64**, и четыре запроса полного состояния подряд с шагом ровно 10 секунд — это
`ClientGameStateManager.FullStateTimeout`. Каждый истёкший таймаут зовёт `OnFullStateRequested`,
которая стирает уже полученный мегабайт и просит такой же заново.

### Замер лечения: тот же стенд, с потолком и без

Один и тот же раунд, один и тот же ходящий киборг, окно восемь минут, задержка 300 мс в одну
сторону, ванильные `pvs_range = 25` и `force_ack_threshold = 60`:

| | без потолка (`net.pvs_byte_budget -1`) | с потолком (`0`, авто, доля 50%) |
|---|---|---|
| запросов полного состояния | 26 | %%POT_RESYNC%% |
| полных состояний выброшено клиентом не применив | 2 (4.87 МБ впустую) | %%POT_DROP%% |
| переполнений буфера состояний | 2 | %%POT_OVER%% |
| `PartialStateReset`, удалено за раз (максимум) | 60 сущностей | %%POT_DEL%% |
| поток к клиенту, медиана / p90 | 107 / 227 КБ/с | %%POT_RATE%% |
| отставание ack, медиана / p90 | 21 / 53 тика | %%POT_LAG%% |

Базовый случай воспроизводит боевой почти точь-в-точь: полные состояния 234 КБ против 242 КБ,
195 фрагментов против 202, та же форма отставания подтверждения. То есть стенд меряет ту же
болезнь, а не похожую.

### Почему отвергнуто

Замысел был: реже отправлять — значит слипать правки, потому что дельта считается от
подтверждённого тика, а не от предыдущей отправки. Сущность, дёрнувшаяся тридцать раз за
секунду, уехала бы одним итоговым значением вместо тридцати.

**На этой нагрузке слипать нечего.** Трафик станции — это не одна сущность, дёргающаяся тридцать
раз, а сотни РАЗНЫХ сущностей, каждая по разу. Слипание не уменьшает объём, оно только
складывает тридцать мелких пакетов в один большой. А большой пакет на надёжном канале строго
хуже: то, что раньше уезжало ненадёжной датаграммой ниже MTU, теперь обязано ехать надёжно и
занимать окно из 64 сообщений.

Замер, стенд, восемь минут, задержка 300 мс в одну сторону, один и тот же ходящий киборг:

| | без потолка | с потолком (авто, 50%) |
|---|---|---|
| запросов полного состояния | 11 | 0 |
| поток к клиенту, медиана | **109 КБ/с** | **208 КБ/с** |
| состояний за 30 тиков | 30 | **1** |
| размер одного состояния | 3.6 КБ | **213 КБ** |
| надёжным каналом | 100% (медиана) | 100% |
| отставание ack, медиана | 19 тиков | 62 тика |

Ресинков ноль — и это единственное, что стало лучше. Всё остальное стало хуже: вдвое больше
байт, одно обновление в секунду вместо тридцати, отставание подтверждения втрое. Играть на таком
нельзя, а ноль ресинков получен не лечением, а тем, что клиент перестал успевать замечать
поломку.

### Две ошибки внутри самой правки, найденные по дороге

Обе стоят записи: они не про эту меру, а про то, как вообще устроен PVS.

1. **Полное состояние списывалось с бюджета.** Оно потолок не спрашивает, поэтому долг копился
   быстрее, чем пополнялся: четверть мегабайта — почти четыре секунды тишины, всплеск прибытия
   шаттла в 6.8 МБ — полторы минуты. Клиент получал 0.7 КБ/с вместо 64. Виновника назвал живой
   опыт: `net.pvs_byte_budget -1` на работающем сервере немедленно вернул 123 КБ/с.
2. **Порог принудительного подтверждения был переставлен с тиков на число отправок.** Довод был
   верный — такт, пропущенный сервером, не должен идти клиенту в счёт отставания. Вывод неверный:
   апстримовый предел ограничивает не число отправок, а ВОЗРАСТ базы дельты. Без него потолок
   складывается в равновесие: сервер молчит — база стоит — состояние растёт — молчать приходится
   дольше. Замер до починки: отставание подтверждения 3924 тика (130 секунд). Правильно —
   оба предела сразу, по тикам и по числу отправок.

### Что из этого следует оставить

Число, ради которого всё делалось: **надёжный канал Lidgren отдаёт 64 сообщения за круг RTT**
(`NetConstants.ReliableOrderedWindowSize`, и окно жёсткое на обеих сторонах — приёмник заводит
такое же, поэтому поднять его только у сервера нельзя). При MTU 1200 и RTT 600 мс это 128 КБ/с.
Боевой раунд 23.08 предлагал p90 335 КБ/с — в 2.6 раза больше. Лечить это надо не темпом
отправки, а **числом и размером полных состояний**: 1728 штук по 242 КБ за раунд, 545 МБ.


### Как устроено, если включать

`TryTakeSendSlot` — ведро токенов на сессию. Пополняется раз в такт, тратится по фактическому
размеру пакета на проводе (`msg.MsgSize`, то есть после сжатия), уходит в минус на полном
состоянии; пока долг не выплачен, обычные состояния этому клиенту не считаются и не отправляются.
Полное состояние потолок не пропускает никогда: оно не поток, а замена мира.

Потолок берётся **из самого соединения**, а не одним числом на всех:
`64 × INetChannel.CurrentMtu × 1000 / INetChannel.Ping` байт в секунду, от него
`net.pvs_byte_budget_share` (умолчание 50%). На локальной сети с RTT 1 мс это 76 МБ/с, то есть
потолка фактически нет; при RTT 600 мс — 64 КБ/с. Фиксированное число, годное для второго,
душило бы первого в шестьсот раз.

`net.pvs_byte_budget`: ноль (умолчание) — считать по соединению; положительное — жёсткое число;
**отрицательное — вести себя как апстрим**, и это выключатель на случай, если правка окажется
вредной.

**Две границы, которые пришлось поставить по замеру, а не по рассуждению.** Первая версия
списывала с бюджета ВСЁ, включая полное состояние, и не ограничивала долг снизу. На стенде это
дало не лечение, а тишину: четверть мегабайта полного состояния при бюджете 64 КБ/с — почти
четыре секунды долга, всплеск прибытия шаттла (6.8 МБ за секунду) — полторы минуты, и клиент
получал **0.7 КБ/с вместо 64**, пока долг рассасывался. Переключение `net.pvs_byte_budget` в −1
на живом сервере немедленно возвращало 123 КБ/с — так виновник и был назван.

Поэтому: полное состояние с бюджета **не списывается** (потолок оно и так не спрашивает, а на
время его полёта дельты молчат по патчу №6), и ведро **не уходит ниже минус одной секунды**
бюджета. Потолок обязан сглаживать поток, а не наказывать за прошлое.

**Почему пропускать такты безопасно.** Дельта считается от `FromTick`, то есть от подтверждённого
клиентом тика, а не от предыдущей отправки. Пропущенное содержимое целиком войдёт в следующий
пакет. Правки не теряются — они СЛИПАЮТСЯ: сущность, дёрнувшаяся тридцать раз за секунду, уезжает
одним итоговым значением вместо тридцати. Поэтому потолок снижает не только темп, но и суммарный
объём.

### Риск

Реже обновление у клиента на плохом канале — но «реже» здесь измеряется относительно того, что он
и так не успевал принять. Доля 50% выбрана с запасом на полное состояние и прочий надёжный
трафик; если ощутимо мешает отзывчивости, поднимать `net.pvs_byte_budget_share`, а не выключать.

Порог принудительного подтверждения при включённом потолке считается по числу ОТПРАВЛЕННЫХ
состояний (`SentSinceAck`), а не по тикам: такт, который сервер пропустил сам, не должен идти
клиенту в счёт отставания, иначе сервер подтвердил бы состояние авансом и вернулась бы поломка
патча №3.

## Патч №6 — пока полное состояние в пути, дельты молчат

**Файлы:** `Robust.Server/GameStates/PvsSystem.cs` (`ShouldWaitForFullAck`),
`PvsData.cs` (`FullSentAt`, `LastRealAck`), `PvsSystem.Ack.cs`, `PvsSystem.Send.cs`.

### Что не так в апстриме

Отправив полное состояние, сервер тут же продолжает слать дельты. Клиент в это время сидит в
`WaitingForFull` и всё приходящее откладывает в буфер, применить не может. На коротком канале это
незаметно. На длинном дельты занимают надёжный канал ВПЕРЕДИ самого полного состояния, из-за
которого клиент и остановился, и растягивают его доставку на кратные RTT.

### Правка

От отправки полного состояния и до **живого** подтверждения этому клиенту не считается и не
отправляется ничего. Живого — то есть `LastRealAck`, отдельной отметки, которую ведёт
`PvsSystem.Ack.cs` ДО проверки на устаревание: `LastReceivedAck` для этого не годится, он прыгает
вперёд на принудительном подтверждении, после чего настоящие подтверждения клиента отбрасываются
как устаревшие.

Молчание безопасно: `FromTick` стоит на тике полного состояния, поэтому всё накопленное войдёт в
первый же пакет после подтверждения. Сторож по времени (15 секунд) обязателен: если полное
состояние всё-таки не доедет, клиент перезапросит его сам, и молчать вечно нельзя.

### Риск

Один круг RTT тишины после каждого полного состояния. С патчем №5 полное состояние получает канал
целиком и доезжает за 1–2 секунды вместо десятков, так что сторож в 15 секунд перестал быть
достижимым.

## Патч №7 — «предыдущий посчитанный такт» вместо `CurTick - 1`

**Файлы:** `Robust.Server/GameStates/PvsSystem.Session.cs` (`LastComputedTick`),
`PvsSystem.ToSendSet.cs` (`IsEnteringPvsRange`), `PvsSystem.cs` (проверки под `#if DEBUG`).

Это не самостоятельное лечение, а обязательное следствие ЛЮБОГО пропуска такта — а такты
пропускает патч №6 (молчание на время полёта полного состояния) и пропускал бы отвергнутый №5.

Апстрим вправе писать `CurTick - 1`: у него состояние считается каждый такт без исключений. Если
такт пропущен, ломаются сразу три места:

* `LastSent` берётся как `PreviouslySent[CurTick - 1]` и на пропуске протухает вместе со списком
  уже освобождённых индексов; `ProcessLeavePvs` идёт по нему и **роняет сервер**;
* `IsEnteringPvsRange` сравнивает `LastSeen` с `CurTick - 1` и после пропуска считает ВСЮ зону
  видимости входящей — то есть шлёт её полными состояниями вместо дельт, и потолок сам же
  раздувает следующий пакет;
* бюджет входа при этом забивается целиком, вытесняя остальную станцию.

Правка: сессия помнит `LastComputedTick` — последний такт, на котором её состояние действительно
считалось, — и все три места сравнивают с ним. Ветка `else` (сбросить `LastSent` в `null`, если
записи нет) обязательна по той же причине: иначе `ProcessLeavePvs` получит протухший список.

**Первая попытка была другой и неверной:** пропускать такт целиком, вместе с расчётом. Так дешевле,
но именно она и ломала эти инварианты. Сейчас состояние считается каждый такт, а экономится ровно
то, что и было целью: сериализация, сжатие и байты на проводе.

## Патч №8 — вернувшейся сущности полное состояние, если отметка подтверждения отстала

**Файл:** `Robust.Server/GameStates/PvsSystem.ToSendSet.cs`, обе ветки `entered`.

### Что не так в апстриме

«Входящая» сущность всегда собирается дельтой от `EntityLastAcked` — от той версии, которую
сервер СЧИТАЕТ подтверждённой клиентом. Приём верен ровно пока клиент эту сущность у себя держит.
Если `EntityLastAcked` старше `fromTick`, значит в последнем подтверждённом состоянии её не было,
и никакой гарантии уже нет: клиент мог удалить её при `PartialStateReset`.

### Замер

Слежка за конкретной сущностью (`PvsSession.DiagWatch`, диагностика №9), боевой раунд 21.08.2026:

```
тик 7978, «полным состоянием», fromTick 7964, EntityLastAcked 7886
```

Отметка отстала от `fromTick` на 78 тиков — больше всей истории отправок, поэтому
`ProcessQueuedAck` не нашёл набор отправленного и не сдвинул её. Сервер собрал дельту от 7886, у
клиента сущности не было, `MetaDataComponentState` в дельту не попал — `MissingMetadataException`,
удаление, запрос полного состояния. Каждые сто тиков, круг за кругом.

### Правка

При `EntityLastAcked < fromTick` собирать полное состояние сущности. Случай «сущность не уходила и
отметка свежая» оптимизацию сохраняет — там гарантия есть. `EntityLastAcked == 0` попадает сюда
сам собой: ноль всегда меньше `fromTick`, а дельта от нуля и была полным состоянием.

### Риск

Один увесистый пакет на сущность там, где раньше был лёгкий, — но только когда сервер уже не
знает, что у клиента есть. Дешевле, чем полный мир.

## Патч №12 — не отвечать вторым полным состоянием, пока первое в пути

**Файл:** `Robust.Server/GameStates/PvsSystem.cs`, метод `OnClientRequestFull`.

> **НЕ ПОДТВЁРЖДЁН ЗАМЕРОМ.** Реализован, собран, на стенде **ни разу не сработал**, потому что
> тот прогон прошёл вовсе без ресинков. То есть он не опровергнут — он не проверен. Прежде чем
> считать его лечением, нужен прогон, в котором ресинки есть; см. «О разбросе стенда» ниже.

### Что не так в апстриме

Клиент просит полное состояние на КАЖДУЮ сущность без метаданных и, сверх того, раз в десять
секунд по своему таймауту (`ClientGameStateManager.FullStateTimeout`). Пока предыдущее полное
состояние летит, все эти просьбы — про одну и ту же беду, а ответ на каждую стоит четверти
мегабайта в канале, который отдаёт 64 сообщения за круг RTT.

Боевой раунд 23.08.2026: **1728 полных состояний по 242 КБ, 545 МБ за смену**. Каждое из них само
создаёт затор, из которого рождается следующая просьба.

### Правка

Не обслуживать просьбу, если предыдущее полное состояние ушло меньше `net.force_ack_threshold`
тиков назад и ещё не подтверждено **живым** ack (`LastRealAck`, а не `LastReceivedAck`: второй
прыгает вперёд на принудительном подтверждении и здесь соврал бы).

Две секунды — столько полное состояние едет даже на длинном канале. Если оно всё-таки не доехало,
клиент спросит снова по своему таймауту в десять секунд, и та просьба будет обслужена. Без мира
клиент не остаётся никогда, а пачка дубликатов схлопывается в один ответ.

### Риск

Задержка восстановления до двух секунд в случае, когда полное состояние действительно потерялось
целиком. Против этого — те же две секунды против нынешних десяти на КАЖДЫЙ лишний мегабайт.

## Патч №13 — полное состояние не двигает пер-сущностные подтверждения

**Файлы:** `Robust.Server/GameStates/PvsSystem.Send.cs` (`SendSessionState`),
`Robust.Server/GameStates/PvsSystem.Serialize.cs` + `PvsSystem.ToSendSet.cs` (`SkipStates`),
`Robust.Server/GameStates/PvsSystem.cs` (`TryTakeSendSlot`).

> **НЕ ПОДТВЕРЖДЁН ЗАМЕРОМ НА БОЮ.** Найден чтением кода при разборе раунда 205 (24.08.2026);
> на внутрипроцессном стенде петля того раунда не воспроизводится (см. тест
> `WalkingEntity_SingleResync_DoesNotLoop` — зелёный и до правки), потому что стендовый клиент
> честен: применяет всё, что подтверждает. Правка закрывает доказанную кодом дыру, но полная
> картина раунда 205 требует ещё и клиентской половины — для неё в этот же деплой добавлена
> диагностика (имя сессии в PVS WATCH, проверка полноты полного состояния, цепочка родителей
> в жалобе).

### Что не так (в этот раз — в нашем же патче поверх апстрима)

`SendSessionState` прогонял полное состояние через ту же ветку аванса, что и порог принудительного
подтверждения: `LastReceivedAck = CurTick` плюс постановка в `PendingAcks`. `ProcessQueuedAck`
после этого записывал `EntityLastAcked = <такт полного>` **каждой сущности зоны видимости — в
момент, когда клиент ещё не получил ни байта**.

Это тот же класс ошибки, который патч №3 убирал у тяжёлых дельт: подтверждение авансом там, где
оно не задумано. Последствие хуже, чем у дельт: если клиент полное состояние не применил —
потерял, отбросил из-за нового запроса, применил не целиком — сервер не узнает об этом НИКОГДА.
По свежему `EntityLastAcked` ветка `entered` больше не срабатывает (и патч №8 бессилен: он
смотрит именно на `EntityLastAcked < fromTick`), все дельты уходят без метаданных, и каждая —
`MissingMetadataException` у клиента.

Подпись в журнале раунда 205 в точности эта: `дельтой, EntityLastAcked свежий, LastLeftView 0`
у сущности, которой у клиента нет; 704 запроса полного мира за 6 минут у клиента из локальной
сети; каждый запрос называет одну и ту же сущность — шагающего киборга.

### Правка (вторая редакция)

Из прежнего аванса убран ровно один шаг — постановка в `PendingAcks`. Без неё
`ProcessQueuedAck` не бежит по `PreviouslySent[<такт полного>]`, и `EntityLastAcked` двигают
только НАСТОЯЩИЕ подтверждения клиента. Это и есть починка петли: сущность, которую клиент не
подтвердил живым ack, при следующей отправке считается входящей и уедет полным состоянием
сущности (ветка `entered` + патч №8).

`LastReceivedAck = CurTick` при отправке полного ОСТАВЛЕН, и это урок первой редакции, снятой
в тот же вечер. Первая редакция не трогала и его — и убила клиента с пингом 586 мс наповал
(журнал 24.08 15:29–15:53, две попытки войти в раунд, обе кончились выходом): база дельт
застревала на такте запроса, каждая дельта строилась от прошлого в 300+ тиков и весила
3–5 КБ × 30/с ≈ 90–115 КБ/с сплошного надёжного потока, и полное состояние (~200 КБ = 170
фрагментов) не могло пробиться через окно Lidgren в 64 сообщения. Свежая база после аванса —
апстримовое поведение, и оно оказалось несущим.

Цена честности: первый пакет после полного уходит жирным — у всех сущностей зоны
`EntityLastAcked = 0` (их обнулила `ForceFullState`), и все они соберутся полными состояниями
сущностей, пока первый живой ack не расставит отметки. Это ~одно лишнее полное на каждый
запрос полного — против вечной петли это дёшево.

Вторая половина правки — `SkipStates`: судьба отправки решается ДО расчёта (`TryTakeSendSlot`
перенесён перед `ComputeSessionState`), и замолчанный такт ведёт всю бухгалтерию (`ToSend`,
`PreviouslySent`, `LastSeen`, бюджеты — на них инварианты PVS), но не строит ни одного
состояния сущности. Полное состояние не пропускается никогда: `TryTakeSendSlot` отвечает
`true` на `RequestedFull` до всех остальных проверок.

### Риск

Тот жирный первый пакет после полного. И открытый вопрос той же ночи: диагностика «PVS HOLD
ON/OFF» поставлена, потому что в залипших сериях первой редакции удержание дельт
(`ShouldWaitForFullAck`) по журналу не включалось ни на тик («пропущено бюджетом 0» при
летящем полном), и это пока не объяснено. Если HOLD-строки покажут мгновенное снятие по
«живому ack», которого не могло быть, — искать там.


## Патч №14 — полное состояние входящей сущности только в тике появления

**Файл:** `Robust.Server/GameStates/PvsSystem.ToSendSet.cs`, метод `IsEnteringPvsRange`.
Стенд: `Content.AiBench/PvsResyncTests.cs`, `ReentryWithoutAck_DoesNotAccumulateFullStates`.

### Что не так

После патчей №1–№13 клиент перестал просить полный мир (`requested full state` = 0), сервер
шёл 33 мс/такт — а игра на локальной сети всё равно замирала, как только в зоне видимости
оказывался идущий киборг. Это не ресинк и не поиск пути.

`IsEnteringPvsRange` считал сущность входящей, пока `EntityLastAcked == 0` или
`EntityLastAcked < fromTick`, даже если её уже слали прошлый посчитанный такт. Бюджет входа
при этом брался только с `enteredSinceLastSent`. Патч №8 для входящей с отставшим ack собирал
**полное** состояние сущности. Вместе это давало спираль: каждая пачка входа оставалась в
каждом следующем пакете без бюджета, плюс новая пачка.

### Замер

Журнал 26.08.2026, `log_2026-08-25-T09-09-06.txt`. Ресинков 0. `Vortex_rax`, ack в норме 2–3
тика.

Вход в раунд, 10:02:52–10:02:55:

```
вошло 50, новых 50, каждый такт
сущностей в состоянии 200 → 250 → … → 2098
2.7 МБ/с, всё надёжным каналом
ack 2 → 31
```

В раунде, 10:31:21, возврат в зону (`новых 0`):

```
вошло 200
сущностей 616 → 818 → 1019 → 1233 → 1354 за одну секунду
ack 3 → 34
854 КБ/с
```

Состав — `Transform + MetaData + Physics + Fixture` стен, кабелей, решёток. Киборг был запалом
(поддерево, спринт через чанки, двери), не содержимым пакета.

### Правка

`entering` истинно только при `enteredSinceLastSent`. Патч №8 не тронут: первое появление с
отставшим `EntityLastAcked` по-прежнему полное состояние сущности. Повторной пересылки без
бюджета нет. Создание по-прежнему уезжает надёжно (`NewCount > 0`).

### Риск

Если первый пакет с созданием сущности потерян целиком, следующие дельты его не дублируют —
ванильный клиент может запросить полный мир. Против этого уже есть надёжная отправка при
`NewCount > 0` (патч №3) и то, что клиент применяет состояния по порядку. Спираль без потери
пакетов на локалке стоила дороже.


## Патч №16 — вход в пропускаемый такт не считается состоявшимся

**Файл:** `Robust.Server/GameStates/PvsSystem.ToSendSet.cs`, обе `AddEntity`.

### Что не так

Патч №13 считает состояние каждый такт, даже когда пакет не уходит (`SkipStates`: полное
в полёте). Патч №14 считает сущность входящей только если `LastSeen` не равен предыдущему
посчитанному такту. Вместе: сущность, вошедшая в зону **во время удержания**, получает
`LastSeen` как обычно, клиенту не отправляется, и после снятия HOLD `enteredSinceLastSent`
ложно. Дальше — дельта без метаданных, `MissingMetadataException`, новый полный мир, новое
удержание, в него входят следующие сущности.

Раунд 230 (26.08.2026), `rewin123`, скрытый злой ИИ, киборгов нет. За пять минут 8 разных
тел без метаданных, у всех `дельтой, EntityLastAcked свежий, LastLeftView 0`: грид на входе,
мышь, сварка в ящике, лёгкие в Bandito, drain, пакет, форма КМа в комоде. Между жалобами —
HOLD 130–180 тиков. Затем клиент зациклился на полном на тик 75714 каждые 10 с.

### Правка

Если `SkipStates && entered` — не ставить `LastSeen` и не класть в `ToSend`. На первом
отправляемом такте вход честный, уезжает полным состоянием сущности (патч №8). Уже видимым
`LastSeen` по-прежнему ставится (инвариант патча №13 / leave). В `AddEntity` для карты/грида
возвращаем `true`, не `false`: `false` оборвал бы чанк как исчерпание бюджета.

Плюс патч №12: не слать второе полное, пока `FullSentAt` жив и нет живого ack. Прежний порог
в 2 с (`ForceAckThreshold`) отпускал следующее полное раньше, чем первое доезжало; клиент
стирал буфер своим таймаутом в 10 с.

### Риск

Сущность, вошедшая в удержание, появится у клиента на тик позже снятия HOLD — это и есть
честная доставка.


## Патч №19 — не класть полное и дельты в полную трубу Lidgren

**Файлы:** `PvsSystem.cs` (`TryTakeSendSlot`, `ShouldWaitForFullAck`, `OnClientRequestFull`),
`PvsSystem.ToSendSet.cs`.

> Замер, на котором написано: раунд 236, 26.08.2026, `rewin123`, ping 400–880 мс, vis ≈ 2800.
> Восемь полных по 218 КБ за минуту, `asked=92314` не двигается, очередь Lidgren 1600–6700,
> HOLD снимался сторожем через 15 с (`reason=watchdog`), киборгов нет.

### Что не так

Надёжное окно Lidgren — 64 **сообщения**. `MsgState` крупнее MTU режется на фрагменты, и
**каждый фрагмент занимает слот** (`SendFragmentedMessage` кладёт чанки по одному в очередь).
Полное на 218 КБ при MTU 1200 — ~180 слотов. Дельта на 3 КБ — 3 слота.

Пока очередь уже тысячи, полное садится в хвост. Сторож HOLD считал 15 с от **отправки**,
не видя трубы: за 15 с схлывало ~1100 слотов, полное даже не начинало передаваться. Ванильный
клиент через 10 с просит снова, `ForceFullState` кладёт ещё одно 218 КБ в тот же хвост.
Байтовый потолок (патч №5) это не лечит: он отвергнут, потому что пропускает такты и слипает
дельту в один пакет на 213 КБ — ещё хуже для окна.

### Правка

Не слать полное, пока `queued + inflight > 8`. `RequestedFull` жив, дельты молчат, труба
схлывает; полное уходит первым, когда есть куда. Повторную просьбу, пока первое ещё не ушло,
не обслуживать (не сбрасывать историю каждые 10 с).

Дельту не класть при `queued + inflight > 48` — оставить слоты под полное и leave. Это не
байтовый бюджет: режем по фактической трубе, пакет не слипается в 200 КБ.

HOLD не снимать сторожем, пока в трубе ещё что-то есть (потолок 60 с). Снимать по живому ack.
Снятие по пустой трубе (`empty`, три RTT от отправки) оказалось дырой — патч №20.

### Риск

Полное, запрошенное при очереди в тысячи, дождётся схлыва — вход в раунд может занять
десятки секунд вместо мгновенного виса. Повторные просьбы клиента в это время игнорируются.
Если соединение умерло, 60 с — последний предел HOLD.

## Патч №20 — не снимать HOLD полного состояния по пустой трубе Lidgren

**Файлы:** `PvsSystem.cs` (`ShouldWaitForFullAck`, `OnClientRequestFull`).

> Замер: раунд 241, 26.08.2026, `rewin123`, ping 350–560 мс, vis ≈ 3100, киборги поддержки.
> 148 полных по ~208 КБ за пять минут, каждое с `причина=empty`. Клиент — чёрный экран, затем
> раунд 242: часть мира двигается, часть лагает, куски стен пропали.

### Что не так

Патч №19 снимал HOLD, когда `queued+inflight == 0` дольше трёх RTT **от отправки**. Пустая
труба значит только то, что фрагменты ушли из окна сервера. 208 КБ — ~143 фрагмента в окне
из 64: передача сама длиннее трёх RTT на пинге 500 мс, и HOLD отпускал в тот же тик, когда
последний слот освободился. Игровой ack ещё в пути, клиент в `WaitingForFull`. Сервер слал
дельты и leave-PVS, клиент их выбрасывал или применял наполовину — MissingMetadata на шасси
киборга, новое полное, петля.

### Правка

Снимать HOLD только по живому ack (`LastRealAck >= FullSentAt`). Пока труба пуста и ack нет —
молчать. Повторную просьбу клиента обслуживать, только если труба пуста **и** прошло ≥ 10 с
(его `FullStateTimeout`); иначе второе полное сотрёт первое на клиенте. Сторож 60 с не
отпускает дельты, а ставит новое полное в очередь.

### Риск

Клиент, чьё полное потерялось, до 10 с сидит без дельт (чёрный или застывший кадр). Это то
же ожидание, что у ванильного `WaitingForFull`, и лучше дыр в стенах. Мёртвое соединение
по-прежнему упирается в 60 с, после чего полное уходит ещё раз, а не поток дельт.

## Патч №21 — грязная неподтверждённая сущность уходит полным состоянием, не дельтой без метадаты

**Файл:** `PvsSystem.ToSendSet.cs`, оба `AddEntity`, хвост после ветки `entered`.

> Замер: боевой раунд, `rewin123`, ping 260–400 мс, шасси `AiBorgCombatChassis` («Клин»).
> ~25 полных ресинков подряд, все на Клине. `LastLeftView=0`, `LastSeen` свежий,
> `EntityLastAcked=0`, сервер пишет «дельтой». Стык в том же vis-дампе не цитируется.

### Что не так

Входящим (дырка в `LastSeen`) патч №8 уже шлёт `GetFullEntityState`, если клиент сущность не
подтверждал. Не-входящим грязным хвост другой: `GetEntityState(..., fromTick)`. MetaData с
полного тика не менялась — в дельту не кладётся.

`LastSeen` проставляется на полном слепке и на HOLD-тактах (патч №13 ведёт бухгалтерию,
патч №16 пропускает только *входящих*). После снятия HOLD Клин уже «внутри», грязный каждый
тик (ходьба / внешность / руки), и уходит дельтой без метадаты. Клиент его не создавал —
`MissingMetadataException` — новое полное — круг. Ствол в слоте и `borg_pvs_override` тут ни
при чём: клиент орёт на корпус.

### Правка

Если сущность грязная и `EntityLastAcked == GameTick.Zero` — `GetFullEntityState`, как на
первом появлении. Не `EntityLastAcked < fromTick`: иначе все грязные в зоне на окно ack
снова набирали бы полные стейты без бюджета (то, что снял патч №14). В логах ноль был всегда;
расширять только если Клин всё ещё петляет.

### Риск

Пока живой ack не запишет `EntityLastAcked`, каждая грязная неподтверждённая сущность везёт
полный стейт, а не дельту. Это одно тело, не вся станция: стены не грязные. `ReentryWithoutAck`
остаётся на ветке `entered` и патчем не задевается.

## Патч №22 — не подтверждать создание сущности vis-набором

**Файлы:** `PvsSystem.Ack.cs` (`ProcessQueuedAck`), `PvsData.cs` (`PreviouslyCreatable`),
`PvsSystem.ToSendSet.cs`.

> Замер: раунд 255, 30.08.2026, патч №21 на бою. 21 ресинк за ~минуту (11.3 на 1000 тиков).
> Во всех 21 строках `EntityLastAcked` **свежий** (лаг ~12 тиков = пинг), ноль ни разу.
> `LastLeftView=0`. Жертвы: Клин 13, `SolutionLungGas` у кота 4, сварщик в шкафу 3, stamina 1.

### Что не так

Патч №21 шлёт `GetFullEntityState`, пока `EntityLastAcked == 0`. Это верно. Но
`ProcessQueuedAck` ставил отметку **всей зоне видимости** такта (`PreviouslySent` = `ToSend`),
а не тем, у кого в пакете была MetaData. Клиент (ванильный) подтверждает состояние в момент
попадания в буфер, не применения. Тонкая дельта или vis-слот без состояния «создают» сущность
на сервере. №21 умолкает. Следующая дельта без MetaData — `MissingMetadataException` —
полное на 250 КБ — HOLD — круг.

Ноль, который видел №21 в `PVS WATCH`, был только на HOLD-тактах (состояние не уходит).
В момент запроса отметка уже свежая. Расширять №21 до `EntityLastAcked < fromTick` нельзя:
отметка не отстаёт от `fromTick`, и это вернул бы аккумулятор патча №14.

Первый ресинк раунда 255 — на массовом входе (50 новых/тик, окно Lidgren забито). Создание
Клину ушло, клиент его не применил, более поздний vis-ack поднял отметку.

### Правка

Параллельно vis-истории держать `PreviouslyCreatable`: сущности, в чьём `EntityState` этого
тика была MetaData. С нуля `EntityLastAcked` поднимать только по этому списку. Кто уже
подтверждён — как раньше, vis-набором. Патч №21 после этого начинает значить то, что на нём
написано: пока клиент не подтвердил пакет **с MetaData**, грязная сущность едет полным
состоянием сущности, а не дельтой.

### Риск

Пока создание не подтверждено, грязные сущности везут полный стейт каждый тик (~RTT, не
станцию). После `ForceFullState` вся зона снова с нуля — первая пачка после HOLD тяжелее;
это плата за повтор, если полное не применилось. `ReentryWithoutAck` на ветке `entered`.

## Порог по пингу: болезнь нелинейна, и в этом всё дело

Замер 24.08.2026, стенд, **три клиента в телах, киборг ходит через всю станцию, окно 30 минут**,
дерево с патчами №1–№4, №6–№8 и №12:

Нагрузка одна и та же: три клиента в телах, шестьдесят бродячих мобов вокруг них, киборг ходит
через всю станцию. Меняется только задержка на ретрансляторе.

| | RTT 600 мс | **RTT 300 мс** |
|---|---|---|
| ресинков за окно | **301** | **0** |
| на 1000 тиков на игрока | **1.26** (боевой раунд 23.08 — 3.31) | **0.00** |
| отставание клиента в момент запроса | медиана **7670** тиков (256 с), максимум 13626 | — |
| отставание ack, медиана / p90 | 19 / 53 тика | **10 / 10** (минимум по RTT — 9) |
| поток к клиенту, медиана | 105 КБ/с | **63 КБ/с** |
| доля состояний надёжным каналом | **30 из 30** | **10 из 30** |
| потолок надёжного канала | 128 КБ/с | 256 КБ/с |
| занято канала | ~85% | **25%** |

Без мобов тот же стенд при RTT 600 давал ноль за десять минут — то есть числа выше получены не
подкруткой пинга, а одной и той же нагрузкой на двух задержках.

**Проверено на боевом конфиге.** Тот же `instances/aksioma/config.toml`, пресет «Злой ИИ
(открытый)», три киборга поддержки на станции, шестьдесят мобов, свой клиент через
`laglink.py --delay-ms 150`, окно 12 минут: **0 ресинков**, отставание ack медиана 10 / p90 10 /
максимум 22 тика, поток 43 КБ/с. То есть результат получен не на игрушечной песочнице.

Стендовая посадка клиента в тело — команда `aibench join <имя>`
(`Content.Server/AiAgent/Commands/AiBenchCommand.cs`). Без неё headless-клиент остаётся в лобби с
пустой зоной видимости, и стенд честно показывает ноль ресинков просто потому, что серверу нечего
слать. На эту ловушку я потратил два прогона.

**Почему вдвое меньший пинг даёт не вдвое, а на порядок лучше.** Размер состояния — это
произведение темпа изменений на ширину окна дельты, а ширина окна равна задержке подтверждения,
то есть RTT. Удвоив RTT, мы удваиваем размер состояния — и оно переходит порог MTU. За порогом
включается совсем другая физика: пакет обязан ехать НАДЁЖНЫМ каналом, а надёжный канал отдаёт
64 сообщения за круг RTT, то есть при удвоенном RTT ещё и вдвое меньше. Нагрузка на надёжный
канал вырастает вчетверо, ёмкость падает вдвое — восьмикратный разрыв из двукратного пинга.

Отсюда практический вывод, которого не было ни в одном документе: **порог играбельности лежит не
там, где кончается терпение игрока, а там, где состояние перестаёт помещаться в датаграмму.**
При MTU 1200 и этой станции он приходится куда-то между 300 и 600 мс.

## О разбросе стенда, и почему лечение пока не подтверждено

Три прогона базового случая при одних и тех же настройках дали **26, 9 и 11** запросов полного
состояния за восемь минут, а четвёртый, отличавшийся только патчем №12 (который в нём не
сработал ни разу), — **0**. То есть собственный разброс стенда перекрывает величину, которую надо
измерить.

Отсюда правило для следующего захода: **одно восьмиминутное окно ничего не доказывает.** Нужен
либо прогон в десятки минут, либо стимул, который даёт ресинки в каждом окне: у боевого сервера
их обеспечивали двое живых игроков, четыре киборга и злой ИИ, ломающий станцию, — на стенде же
ходит один робот по пустому коридору.

## Диагностика №9 — три числа PVS в строке о ресинке

**Файл:** `Robust.Server/GameStates/PvsSystem.cs`, метод `OnClientRequestFull`.

> **В PR не идёт.** Это замер, не лечение. Причина найдена (патчи №3 и №4); строку можно
> оставить, пока живые раунды не подтвердят ноль ресинков на ванильной дальности.

### Зачем

По журналу нельзя отличить две поломки, которые выглядят одинаково («получил сущность без
метаданных»), а лечатся противоположно.

Возврат сущности в PVS шлёт не полное состояние, а **дельту от `EntityLastAcked`**
(`PvsSystem.ToSendSet.cs`, ветка `entered`) — осознанная оптимизация, чтобы не пересылать
вернувшийся в поле зрения предмет целиком. Она верна ровно пока сервер и клиент согласны, какая
версия сущности у клиента есть. Клиент при уходе сущность не удаляет, а помечает `Detached`
(`ClientGameStateManager.QueuePvsDetach`), причём отцепление бюджетировано
(`net.pvs_exit_budget`).

| что в строке | какая поломка | где лечить |
|---|---|---|
| `LastLeftView` ≥ запрошенного тика | сущность уходила из вида и вернулась — виновата оптимизация возврата | полное состояние сущности на возврате |
| `LastLeftView` мал, `EntityLastAcked` велик | из вида не уходила, подтверждение записано авансом | сторона подтверждений |

Наблюдение, ради которого замер и понадобился: после патчей №1 и №2 **все до одной** оставшиеся
потери приходятся на движущихся киборгов (`Клин` 18, `Стык` 9 за прогон), период повтора ~74 тика.
Движутся они штатно — через `InputMoverComponent.CurTickSprintMovement`, то же поле, куда клиент
живого игрока кладёт нажатые стрелки, — то есть особенным их делает не способ движения, а то, что
это чужой движущийся моб с поддеревом, постоянно пересекающий границу чужого PVS.

### Правка

В строку предупреждения добавлены `EntityLastAcked`, `LastLeftView` и `LastSeen` потерянной
сущности. Апстрим такую строку уже пытался написать и закомментировал — ниже стояло
`//sb.Append($" Entity last seen: ...")`, — но она не собиралась: `PvsData` сессии лежит в
`DataMemory` по индексу из метаданных, а не в самих метаданных.

## Почему лечение обязано быть серверным

Соблазн починить это на клиенте велик: половина механики петли живёт в
`Robust.Client/GameStates`. **Правки клиентского движка до игроков не доезжают.**

Сервер раздаёт клиент через ACZ (`[build]` в конфиге нет, `/info` отвечает `"acz": true`), но ACZ
пакует только **контент**: `DefaultMagicAczProvider.Package` зовёт `WriteContentAssemblies` и
`WriteClientResources`, и ничего больше. Сам движок лаунчер берёт со своего CDN по полю
`engine_version` из того же `/info`. То есть `Content.Client.dll` — наш, `Robust.Client.dll` —
ванильный.

Проверка, а не рассуждение: в `bin/` до 24.08.2026 лежала **Debug**-сборка, где
`EXCEPTION_TOLERANCE` не определён, а значит `catch (MissingMetadataException)` не компилируется и
поле `MissingEntity` в запросе полного состояния не заполняется никогда. В боевом журнале это поле
заполнено у каждого игрока. Значит движок у них не наш.

Отсюда правило: **всё, что лечит болезнь, живёт в `Robust.Server`/`Robust.Shared`**. Клиентские
правки допустимы только как стендовая диагностика или как заготовка PR апстримом.

## Диагностика №10 — что случилось с сущностью на клиенте

**Файлы:** `Robust.Client/GameStates/ClientGameStateManager.cs`,
`Robust.Client/GameStates/GameStateProcessor.cs`.

> **В PR не идёт как есть.** Замер, не лечение; до игроков не доезжает (см. раздел выше). Живёт
> ради стенда.

Серверный журнал знает только «клиент получил сущность без метаданных» и не различает три случая,
которые лечатся по-разному: сущность не создавалась никогда; создавалась и снесена
`PartialStateReset`; создавалась и удалена состоянием. Клиент теперь пишет:

* `PartialStateReset до тика N: в состоянии K сущностей, УДАЛЕНО D, например: ...` — и **ждали ли
  мы это полное состояние**. Флаг снимается ДО `OnFullStateReceived`, иначе он всегда `false`;
* `НЕТ МЕТАДАННЫХ у X: последнее событие «...» на тике N` — история сущности из кольца
  `_forkLife`, плюс границы состояния, `LastRealTick` и размер буфера;
* `ВЫБРАСЫВАЮ полученное полное состояние / N буферизованных состояний` в
  `OnFullStateRequested` — то самое место, где таймаут стирает уже доехавший мегабайт;
* предупреждение о переполнении буфера состояний — было под `#if FULL_RELEASE`, то есть на стенде
  пропадало молча.

Сводит клиентский и серверный журналы `Tools/pvs_client_report.py`.

## Диагностика №18 — трасса канала, ack и киборгов (`NET TRACE`)

**Файлы:** `Robust.Shared/Network/NetReliableWindow.cs`, `INetChannel.GetReliableWindow`,
`Lidgren.Network/NetConnection.GetReliableChannelDepth`, `PvsSystem.Trace.cs`,
`Tools/net_trace_report.py`. CVar: `net.pvs_trace` (умолчание 2).

> **В PR не идёт.** Замер, не лечение. Ванильный клиент не затронут.

После патчей №1–№16 в боевом журнале кончились детектируемые ресинки, а вис остался — и при
идущем киборге, и без движения. Сводка раз в 30 тиков не ловит такт, на котором:

* окно Lidgren (`ReliableUnordered`, 64 слота) встаёт — `free≤0`, `queued>0`;
* `MsgStateLeavePvs` отбирает те же слоты, что и состояние;
* `FromTick` стоит, дельта растёт;
* ack не находит `PreviouslySent` (`ack_miss`) или отбрасывается как устаревший после аванса;
* киборг пересекает PVS-чанк, и в том же окне тиков скачет размер пакета.

Строка одна на событие, префикс `NET TRACE`, поля `k=v`. Разбор:

```sh
python3 Tools/net_trace_report.py <журнал сервера>
```

Уровни: 0 — как раньше (ресинк/HOLD/жирное/полное); 1 — сводка раз в секунду; 2 — аномальные
такты (умолчание); 3 — каждый такт, только короткий захват. Живьём: `cvar net.pvs_trace 3`.

Lidgren отдаёт глубину канала и в Release: `PacketSent`/`MessageResent` под `#if DEBUG`, а
`GetReliableChannelDepth` читает живые очереди. Без этого поля в журнале не было ни разу.

## Правка клиента №11 — не подтверждать состояние, которое выброшено

**Файл:** `Robust.Client/GameStates/GameStateProcessor.cs` (`TryAdd`, `AddNewState`).

Строка над `HandleStateMessage` в апстриме гласит: «We ONLY ack states that are definitely going
to get applied. Otherwise the server might assume that we applied a state containing
entity-creation information, which it would then no longer send to us». Условие нарушено самим
кодом: `TryAdd` при переполнении буфера молча выбрасывает состояние, а `AddNewState` всё равно
возвращает `true`.

Правка: `TryAdd` возвращает исход, `AddNewState` — его. Три строки.

**До игроков не доезжает** (см. раздел выше) и потому в счёт лечения не идёт; держится как
заготовка PR апстримом и как честность стенда.


## Как это проверяется

```sh
# стенд в одном процессе: разрушение мира клиента полным состоянием
# и аккумулятор полных стейтов при возврате в зону без ack (патч №14)
dotnet test Content.AiBench --filter PvsResync

# стенд с настоящей задержкой: сервер, ретранслятор, headless-клиент
python3 Tools/laglink.py --listen 1223 --target 1212 --delay-ms 300 --csv /tmp/link.csv
# ...клиент подключается на 1223; журнал ретранслятора и есть съём трафика

# что случилось у клиента и у сервера, сведённое по тикам
python3 Tools/pvs_client_report.py <журнал клиента> <журнал сервера>

# вис без ресинков: окно канала, ack, leave, киборги
python3 Tools/net_trace_report.py <журнал сервера>

# боевой раунд: та самая сравнимая величина
python3 Tools/pvs_resync_report.py <журнал сервера>
```

**Собирать только в Release.** `EXCEPTION_TOLERANCE` определяется лишь в конфигурациях `Release` и
`Tools` (`RobustToolbox/MSBuild/Robust.DefineConstants.targets`), а без него
`MissingMetadataException` не превращается в запрос полного состояния — воспроизводится не та
болезнь. `net.fakelagmin` для задержки не годится: симуляция в Lidgren живёт под `#if DEBUG`.

Цель — **ноль ресинков на 1000 тиков на игрока** при ванильных `pvs_range = 25` и
`force_ack_threshold = 60`, на клиенте с пингом ~600 мс и с включёнными киборгами поддержки.
